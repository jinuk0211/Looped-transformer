**2. 반복형 아키텍처는 무엇을 바꾸는가**

《디 인포메이션》의 보도에 따르면, GPT 6 Astra는 **반복형 트랜스포머(looped transformer)** 구조를 사용한다.

OpenAI가 전체 기술 사양을 공개하지 않았기 때문에 정확한 구현 방식은 알려져 있지 않다. 다만 이 구조의 기본 원리는 이미 공개된 연구를 통해 상당 부분 이해할 수 있다.

기존 트랜스포머에서는 모델의 내부 상태인 ‘은닉 상태’가 각 연산 블록을 한 번씩 통과한다. 반면 반복형 트랜스포머는 한 블록에서 나온 결과를 다시 같은 블록에 넣어 처리할 수 있다.

쉽게 말하면 **모델 내부에서 초안을 여러 번 다듬는 방식**이다.

먼저 초기 표현을 만들고, 같은 가중치를 사용하는 연산을 다시 거치면서 이를 개선한다. 이 과정을 여러 차례 반복한 뒤에야 사용자에게 보이는 다음 토큰을 출력한다.

이때 파라미터 수는 그대로다. 매번 같은 가중치를 재사용하므로, 반복 횟수가 늘어나도 반드시 모델 자체가 커지는 것은 아니다. 늘어나는 것은 **연산량**이다.

기존 트랜스포머에서는 하나의 토큰이 서로 다른 블록들을 순서대로 통과한다. 반복형 트랜스포머에서는 같은 구조를 여러 번 통과할 수 있다. 즉, **파라미터를 늘리지 않고도 연산의 깊이를 늘리는 것**이다.

이 구조에서는 다음과 같은 선택이 가능해진다.

* 파라미터를 늘리면 더 많은 메모리가 필요하다.
* 반복 횟수를 늘리면 더 많은 연산이 필요하다.
* 하나의 모델이 작업에 따라 서로 다른 양의 연산을 사용할 수 있다.

특히 마지막이 중요하다. 새로운 모델을 만들지 않고도, 문제를 처리하는 연산 깊이를 바꿀 수 있기 때문이다.

**3. 반복적인 연산 깊이는 어떻게 학습시키는가**

트랜스포머 블록을 단순히 반복 실행하도록 만든다고 해서 모든 문제가 해결되지는 않는다.

학습할 때 항상 정확히 32번씩 반복한다고 해보자. 그러면 모델은 각 반복 단계의 순서에 의존하는 방식을 배울 수 있다. 첫 번째 반복에서는 어떤 일을 하고, 열 번째에서는 다른 일을 하며, 서른두 번째는 최종 출력을 만드는 단계로 굳어질 수 있다.

결국 겉으로만 반복 구조일 뿐, 실질적으로는 고정된 32층 신경망처럼 동작하게 되는 것이다.

연구자들은 이를 방지하기 위해 **학습 중 반복 횟수를 바꾼다.**

대표적인 사례가 반복 깊이 모델인 **Huginn**이다. 연구진은 35억 개의 파라미터를 가진 모델을 약 8,000억 개의 토큰으로 학습시켰다.

각 학습 단계에서는 평균이 약 32인 확률분포에서 반복 횟수를 뽑았다. 어떤 예시는 4번, 다른 예시는 17번이나 40번, 또 다른 예시는 90번에 가깝게 처리할 수 있었다.

따라서 모델은 현재 단계가 마지막 반복인지 미리 알 수 없었다. 정해진 순서대로 작업을 수행하는 것보다 더 일반적인 능력을 배워야 했다.

바로 **현재의 내부 상태를 더 나은 상태로 개선하는 능력**이다.

그런데 수십 번의 반복을 학습시키면 또 다른 문제가 생긴다. 메모리 사용량이다.

일반적인 역전파 방식은 각 반복 단계의 중간 활성값을 저장해야 한다. 반복 횟수가 많아지면 필요한 메모리도 엄청나게 늘어난다.

Huginn 연구진은 현실적인 절충안을 사용했다. 순전파, 즉 실제 계산은 여러 번 반복하되, **기울기는 마지막 8번의 반복 구간에 대해서만 계산**한 것이다.

앞선 반복들도 최종 결과에 영향을 주지만, 그 과정에서 발생한 모든 활성값을 메모리에 보관할 필요는 없어진다.

이는 ‘절단된 시간 역전파’와 비슷하다. 다만 일반적인 순환 신경망처럼 문장의 앞뒤 단어 사이에서 반복이 일어나는 것이 아니라, **하나의 입력을 처리하는 연산 깊이 방향으로 반복이 일어난다**는 차이가 있다.

정리하면, 학습 단계마다 반복 횟수를 새로 뽑고, 역전파는 마지막 8번에만 적용한다.

이 모델이 배우는 것은 ‘정확히 32단계로 이루어진 고정 절차’가 아니다. **언제 반복을 멈추더라도 유용한 답에 가까워지도록 내부 상태를 개선하는 방법**이다.

이렇게 되면 ‘깊이’의 의미도 달라진다. 더 이상 엔지니어가 학습 전에 정해 놓는 구조적 특성에만 머물지 않고, 추론할 때 조절할 수 있는 변수가 된다.

**4. 추론할 때 필요한 만큼 연산하기**

현재 대부분의 추론 조절 방식은 모델이 생성하는 토큰을 중심으로 작동한다.

모델에게 더 오래 생각하도록 하면, 더 긴 사고 과정(chain of thought)을 생성하거나, 출력 토큰을 더 많이 사용하거나, 중간 설명을 추가로 작성하는 식이다.

반복형 구조는 다른 방법을 제공한다.

가중치를 바꾸거나 설명을 길게 쓰게 하지 않아도, 내부 연산의 반복 횟수를 조절할 수 있다. 예를 들면 다음과 같다.

* 간단한 작업: 4번 반복
* 어려운 수학 증명: 32번 반복
* 복잡한 코딩 문제: 64번 반복

모델과 가중치는 그대로다. 달라지는 것은 각 토큰을 처리하기 위해 수행하는 **내부 연산의 양**이다.

공개된 반복 깊이 실험에서도 예상되는 패턴이 나타난다. 초반에는 반복 횟수를 늘릴수록 성능이 빠르게 좋아진다. 이후에는 개선 폭이 줄어들다가 점차 정체된다.

이는 은닉 상태가 어느 정도 수렴하고 있음을 시사한다.

초기 반복에서는 큰 오류를 수정하고, 이후에는 작은 세부 사항을 다듬는다. 그러다가 어느 순간부터는 연산을 더 해도 의미 있는 개선이 거의 일어나지 않는다.

미래의 시스템은 그 시점을 자동으로 감지할 수도 있다.

모든 프롬프트에 똑같은 반복 횟수를 배정하는 대신, 내부 상태가 충분히 안정될 때까지 연산을 이어가는 것이다. 쉬운 토큰은 적은 비용으로 처리하고, 어려운 토큰에는 더 많은 연산을 배정할 수 있다.

이것이 실제로 구현된다면 **문제에 맞춰 연산 깊이를 조절하는 방식**이 된다.

더 오래 생각한다고 해서 반드시 더 많은 글을 써야 하는 것은 아니게 된다.

**5. 관련 연구와 초기 실용적 성과**

트랜스포머의 층을 재사용한다는 발상 자체는 새롭지 않다.

Universal Transformers는 2018년에 반복 처리를 도입했다. ALBERT는 여러 층이 가중치를 공유하게 해 파라미터 수를 줄였다. Mixture of Recursions는 토큰마다 서로 다른 양의 연산을 거치도록 보내는 방법을 탐구했다.

공개 모델인 **Nanbeige4.2 3B**는 특히 직접적인 사례다.

이 모델의 설정에는 22개 층과 `num_loops: 2`가 명시되어 있다. 즉, 22개 층을 두 번 통과한다. 파라미터 수는 대략 22층 모델 수준이지만, 연산 깊이는 약 44층 모델에 해당한다.

22개 층, 반복 횟수 2회, Apache 2.0 라이선스. 반복 구조가 이미 공개 모델의 설정에서 확인되는 것이다.

그동안 반복형 트랜스포머는 흥미로운 연구 주제였지만, 주류 방식으로 자리 잡지는 못했다. 부족했던 것은 **규모를 키워도 효과가 유지된다는 강한 실험적 근거**였다.

9월 1일 공개된 **SMELT**는 반복형 트랜스포머와 기존 트랜스포머를 동일한 조건에서 비교하기 위해 설계된 연구다.

연구진은 파라미터 수, 학습 연산량, KV 캐시 크기를 통제해 비교했다. 그 결과 반복형 모델은 같은 성능에 도달하는 데 필요한 학습 연산량이 **6.8~18% 적었다.** 가장 큰 이득은 코드 분야에서 나타났다.

어텐션의 작동 방식에도 변화가 관찰됐다.

기존 트랜스포머에서는 문장 앞부분의 토큰들이 종종 **‘어텐션 싱크(attention sink)’**, 즉 주의가 과도하게 몰리는 지점이 된다. 의미상 중요하지 않아도 다른 토큰보다 훨씬 많은 주의를 받는 것이다.

그런데 같은 블록을 두 번째로 통과한 뒤에는, 어텐션이 실제로 더 관련 있는 토큰 쪽으로 이동했다.

두 번째 반복은 첫 번째 계산을 단순히 되풀이한 것이 아니다. 첫 번째 결과를 바탕으로 **더 필요한 정보에 집중하는 처리**를 수행한 것이다.

SMELT가 앞으로 모든 모델을 반복형으로 만들어야 한다고 증명한 것은 아니다. 다만 주요 실험 조건을 맞춘 뒤에도 반복 구조가 경쟁력을 유지한다는 점은 보여준다.

이제 질문은 “반복 깊이가 작동하는가?”를 넘어, **“이 방식을 얼마나 큰 규모까지 확장할 수 있는가?”**로 옮겨가고 있다.

**6. 해석 가능성과 통제**

반복 구조의 장점은 동시에 모델을 감시하기 어렵게 만드는 요인이기도 하다.

사고 과정을 명시적인 텍스트로 생성하는 모델은 중간 단계의 일부를 사람이 읽을 수 있다. 연구자는 이를 살펴보며 의심스러운 패턴을 찾고, 모델이 설명한 추론과 최종 답변을 비교할 수 있다.

하지만 반복형 모델은 글을 생성하지 않은 채 내부 활성값에서 더 많은 처리를 수행할 수 있다.

Buck Shlegeris와 Ryan Greenblatt는 이것이 **사고 과정 모니터링의 유용성을 떨어뜨릴 수 있다**고 주장했다. 처리의 더 많은 부분이 보이지 않는 내부 연산으로 옮겨가면, 화면에 나타나는 설명만으로는 모델이 어떻게 결론에 도달했는지 파악하기 어려워질 수 있다는 것이다.

Sebastian Raschka는 여기에 중요한 반론을 제시했다.

가중치를 재사용한다고 해서 자동으로 비밀스럽거나 접근할 수 없는 사고가 생기는 것은 아니다. 내부 활성값은 여전히 해석 가능성 도구로 분석할 수 있다. 주된 차이는 토큰을 출력하기 전에 더 많은 연산을 수행하므로, 겉으로 드러나는 중간 추론 토큰이 줄어들 수 있다는 점이다.

OpenAI의 수석 과학자 Jakub Pachocki도 Astra의 계산 그래프 깊이는 GPT 4의 약 두 배 이내이며, 모니터링 가능성을 유지하기 위해 반복을 의도적으로 제한했다고 밝혔다.

이는 무제한으로 반복하는 구조보다는, 반복 범위를 제한한 구현임을 시사한다.

애초에 사고 과정 텍스트가 모델의 내부 계산을 충실하게 기록한다고 보장할 수도 없다. 모델은 모든 내부 연산을 과학적으로 정확하게 보고하도록 보상받는 것이 아니라, 유용한 답변을 내도록 보상받기 때문이다.

OpenAI, Anthropic, Google DeepMind가 참여한 연구들은 모델의 설명이 중요한 요인을 빠뜨리거나, 이미 내린 결정을 사후에 정당화하거나, 실제 결과에 영향을 준 경로보다 더 깔끔한 추론 경로를 제시할 수 있음을 보여준다.

반복형 구조에서는 이 차이를 더욱 분명하게 인식해야 한다.

**사용자에게 보이는 추론은 하나의 설명 인터페이스일 수 있다.** 핵심 계산은 글이 출력되기 전에 모델 내부에서 이루어질 수 있기 때문이다.

**7. GPT 6 Astra의 평가 결과**

GPT 6 Astra의 가장 눈에 띄는 벤치마크 결과는 **ARC AGI 3에서 기록한 99.9%**다.

거의 완벽한 성능처럼 들리지만, 이 숫자는 평가를 어떻게 실행했는지에 크게 좌우된다.

Simon Willison은 99.9%가 OpenAI의 맞춤형 **Provider Adapter 하네스**, 즉 모델을 실행하고 평가하는 시스템에서 나온 결과라는 점을 강조했다. 같은 모델을 표준 ARC Prize 하네스로 평가했을 때는 62.7%를 기록했다.

모델은 같았다. 달라진 것은 평가 환경이었다.

| 평가 환경            |    점수 |      실행 비용 |
| ---------------- | ----: | ---------: |
| OpenAI 맞춤형 하네스   | 99.9% | 약 19,000달러 |
| 표준 ARC Prize 하네스 | 62.7% | 약 26,000달러 |

두 점수의 차이는 **37.2%포인트**다. 훨씬 높은 점수를 기록한 환경이 오히려 비용도 더 적게 들었다.

그렇다고 이 결과가 반드시 무효라는 뜻은 아니다. 맞춤형 어댑터가 모델과 더 효과적으로 상호작용하거나, 범용 평가 시스템이 끌어내지 못하는 능력을 활용했을 수 있다.

다만 가장 주목받는 숫자를, **그 숫자가 나온 조건과 분리해서 해석해서는 안 된다.**

다른 평가에서는 차이가 이만큼 극적이지 않다.

Artificial Analysis Intelligence Index에서 Astra는 GPT 5.6 Sol과 대체로 비슷한 점수를 기록하고, Claude Fable 5.1보다는 약 5점 낮다.

실용적인 장점은 에이전트 작업에서의 효율성에 있을 수 있다. 경쟁력 있는 성능을 더 낮은 비용으로 달성할 수 있다는 것이다.

벤치마크는 모델이 무엇을 해낼 수 있는지 보여준다. 아키텍처는 그 능력이 어디에서 나오고, 앞으로 어떻게 발전할 수 있는지 이해하는 데 도움을 준다.

**8. 이것이 AI의 미래에 의미하는 것**

오랫동안 언어 모델을 확장한다는 것은 주로 파라미터와 데이터를 늘리고, 트랜스포머 블록을 더 많이 쌓는다는 뜻이었다.

새로운 세대의 모델은 더 커지고, 더 비싸지고, 실행에 더 많은 자원을 요구했다.

GPT 6 Astra는 다른 방향의 가능성을 보여준다.

모델은 같은 파라미터를 재사용하면서 어려운 작업에 더 많은 연산을 배정하고, 첫 단어를 출력하기 전에 내부 표현을 다듬을 수 있다.

이렇게 되면 **모델의 크기와 추론의 깊이를 별도로 조절할 수 있다.**

언제나 똑같이 정해진 계산 경로를 따르는 대신, 개별 문제의 난도에 맞춰 수행하는 연산량을 바꾸는 것이다.

이는 모델의 성능뿐 아니라 AI를 사용하는 비용 구조도 바꿀 수 있다. 같은 모델이 간단한 요청은 빠르고 저렴하게 처리하고, 더 많은 추론이 필요한 작업에서는 연산 깊이를 늘릴 수 있기 때문이다.

언어 모델에서 순환 구조가 다시 주목받고 있다. 다만 이번에는 주로 단어와 단어 사이에서 반복하는 것이 아니라, **단어 하나를 만들어 내는 계산 과정 안에서 반복한다.**

다음 세대의 AI가 더 강력해지는 이유는 단순히 파라미터가 더 많아서만은 아닐 수 있다.

그 핵심 경쟁력은 **언제 충분히 좋은 답에 도달했는지, 언제 내부 연산을 한 번 더 반복할 가치가 있는지 판단하는 능력**이 될 수 있다.

더 큰 문제는 앞으로 이런 내부 추론 능력이 계속 확대될 가능성입니다. 언젠가 AI가 대부분의 추론을 잠재 공간에서 처리하게 된다면, 사람이 체인 오브 소트를 읽어도 AI가 실제로 무엇을 계획하고 있는지 알기 어려워질 수 있습니다. 특히 AI가 의도적으로 감시를 피하려 하거나, 체인 오브 소트를 겉보기에 안전하게 작성하도록 훈련받는 경우에는 더욱 위험합니다.

*프롬프트 캐싱, 지시문, 추론 강도(effort)를 조정하면 애플리케이션의 성능을 유지하면서 Claude 사용 비용을 줄일 수 있다.*

성능과 비용은 흔히 서로 맞바꾸는 관계로 여겨진다. 비용을 줄이려면 결과의 품질도 어느 정도 포기해야 한다는 것이다.

하지만 실제로 Claude Platform을 사용하는 많은 애플리케이션은 다음 세 가지를 개선하는 것만으로도 성능을 유지하면서 비용을 줄일 수 있었다.

* **프롬프트 캐시 적중률을 높인다.**
* **최신 고성능 Claude 모델로 전환할 때, 기존 프롬프트에서 성능을 방해하는 지시를 제거한다.**
* **작업에 맞게 추론 강도를 조절한다.**

우리는 이 지침을 [claude-api 스킬](https://github.com/anthropics/skills/tree/main/skills/claude-api)에 담았다. 이 글에서는 Claude Code와 해당 스킬을 활용해, 성능을 유지하거나 높이면서 비용을 줄이는 방법을 소개한다.

**1. 프롬프트 캐시**

Claude는 답변을 생성하기 전에, 먼저 입력된 프롬프트를 처리해 내부 연산에 사용할 상태를 만든다. 이 단계를 **프리필(prefill)**이라고 하며, 입력 처리 비용에서 큰 비중을 차지한다.

프롬프트 캐싱은 이렇게 계산한 상태, 즉 **KV 캐시(Key–Value cache)**를 저장한다. 이후 요청의 앞부분이 이전 요청과 같으면, 같은 계산을 반복하는 대신 저장된 상태를 불러온다. 캐시를 읽는 비용은 [일반 입력 처리 비용보다 훨씬 저렴하다](https://platform.claude.com/docs/en/about-claude/pricing).

캐시를 효과적으로 사용하려면 세 가지를 알아야 한다.

* **캐시는 특정 모델에 연결된다.** 모델이 바뀌면 기존 캐시를 그대로 사용할 수 없다.
* **캐시를 재사용할 요청의 앞부분은 바이트 단위까지 정확히 같아야 한다.**
* **캐시에는 유효기간(TTL)이 있다.**

이를 고려하면 다음 사항에 주의해야 한다.

**대화 중간에 추론 강도를 바꿀 때 주의하자.**

추론 강도 설정은 사용자 콘텐츠보다 앞쪽에 프롬프트의 일부로 들어가므로, 캐시되는 앞부분에도 영향을 준다. Opus 5와 Fable 5.1을 비롯한 일부 모델에서만 [캐시를 깨뜨리지 않고 대화 중 추론 강도를 변경](https://platform.claude.com/docs/en/build-with-claude/effort#changing-effort-mid-conversation)할 수 있다.

**자주 바뀌는 값을 프롬프트 앞부분에 넣지 말자.**

시스템 프롬프트에 현재 시각이나 동적으로 생성되는 ID를 넣으면, 모델을 호출할 때마다 해당 값이 달라져 캐시를 재사용하지 못할 수 있다.

**도구 정의의 순서가 제멋대로 바뀌지 않게 하자.**

Claude Messages API에서는 프롬프트가 정해진 순서로 구성되며, 도구 정의가 맨 앞에 들어간다. 도구 정의가 변경되면 캐시가 무효화될 수 있다.

**대화를 분기할 때도 주의하자.**

서브에이전트나 분기된 대화가 부모 대화의 캐시를 공유하려면, 요청의 앞부분이 바이트 단위까지 같고 모델과 추론 강도도 동일해야 한다.

**어떻게 개선할 수 있을까?**

우리는 프롬프트 캐시를 관리하면서 다음과 같은 방법이 효과적이라는 것을 확인했다.

* **캐시 적중률을 면밀히 확인한다.**
  [Claude Console과 캐시 진단 API](https://platform.claude.com/docs/en/build-with-claude/cache-diagnostics)는 캐시를 재사용하지 못한 이유를 알려준다. 두 요청을 비교해 프롬프트 앞부분이 정확히 어디서 달라졌는지도 확인할 수 있다.

* **드물게 사용하는 도구는 필요할 때 불러온다.**
  모든 도구를 미리 선언하되, 자주 쓰지 않는 도구에는 [`defer_loading`](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-use-with-prompt-caching#defer-loading-and-cache-preservation)을 설정한다. 이렇게 하면 해당 도구의 정의는 캐시되는 앞부분에서 빠지고, Claude가 도구 검색으로 찾아 사용할 때 대화에 추가된다. 기존 캐시를 유지할 수 있는 것이다.

* **시스템 지시를 바꿀 때는 메시지로 추가한다.**
  일부 Claude 모델은 시스템 프롬프트 자체를 수정하는 대신, 대화 중간에 시스템 지시를 메시지로 추가할 수 있다. 이 방식은 기존 캐시를 유지한다.

* **잘 바뀌지 않는 내용을 앞에 배치한다.**
  도구 정의와 시스템 프롬프트처럼 고정된 내용을 먼저 넣고, 계속 길어지는 대화 기록을 그 뒤에 배치한다.

* **어차피 캐시를 다시 만들어야 할 때 모델이나 추론 강도를 바꾼다.**
  예를 들어 대화 압축(compaction)은 대화 내용을 크게 다시 쓰므로, 기존 캐시의 상당 부분을 새로 만들어야 한다. 이미 캐시 재생성 비용이 발생하는 시점이므로, 모델이나 추론 강도를 바꾸기에도 적절하다.

* **대화가 길어질수록 캐시 저장 경계도 옮긴다.**
  Claude Platform의 [자동 캐싱](https://platform.claude.com/docs/en/build-with-claude/prompt-caching#automatic-caching)을 사용하면, 캐시할 수 있는 마지막 블록에 캐시 경계점을 자동으로 설정할 수 있다.

* **캐시를 미리 준비해 둔다.**
  실제 요청과 같은 추론 강도를 사용하고, 캐시 경계점을 명시한 뒤 `max_tokens: 0`으로 요청을 보낸다. 그러면 답변을 생성하지 않고 프롬프트만 처리해 캐시에 저장한다. 세션 시작 시점이나 사용자가 입력하는 동안 이를 실행하면, 첫 실제 요청부터 준비된 캐시를 사용할 수 있어 지연 시간이 줄어든다.

* **캐시 유효기간을 넘기지 않는다.**
  5분짜리 캐시의 유효기간은 요청이 시작된 시점부터 계산된다. 에이전트가 도구 실행이나 서브에이전트의 응답을 5분 넘게 기다리면, 결과가 돌아오기 전에 부모 대화의 캐시가 만료될 수 있다. 이런 경우에는 프롬프트 앞부분에 [1시간짜리 TTL](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence)을 적용하는 것을 고려하자.

**2. 지시문**

프롬프트에는 모델의 약점을 보완하기 위한 지시가 계속 쌓이기 쉽다. 하지만 모델이 발전하면, 예전에는 도움이 됐던 지시가 최신 모델의 능력과 맞지 않을 수 있다.

다음은 최신 고성능 Claude 모델의 성능을 방해하고, 의도치 않게 비용까지 늘리는 대표적인 **프롬프트 안티패턴**, 즉 피해야 할 지시 방식이다.

| 안티패턴                 | 예시와 문제점                                                                                              |
| -------------------- | ---------------------------------------------------------------------------------------------------- |
| **형식적인 반복 검증**       | “작업을 다시 확인해라”, “응답하기 전에 두 번 검증해라.” 최신 모델은 이를 문자 그대로 수행하면서 불필요한 토큰을 사용할 수 있다.                         |
| **지나친 철저함과 강조**      | “최대한 철저하게 해라”, “매우 중요: 반드시 항상 ….” 이런 지시는 과도하게 긴 답변과 불필요한 도구 호출을 유발할 수 있다.                            |
| **고정된 절차와 사고 기록 양식** | “별도의 작업 메모에 단계별로 생각해라”처럼 정해진 사고 절차를 강제하는 경우다. 모델의 기본 추론 위에 중복 절차가 더해져 토큰이 낭비될 수 있다.                  |
| **오래된 예시**           | 이전 모델의 실수를 보완하려고 만든 예시가, 최신 모델에게는 필요하지 않은 긴 추론 과정을 따라 하게 만들 수 있다.                                    |
| **서로 모순되는 규칙**       | “정책에 맞으면 항상 환불해라”와 “상위 담당자에게 넘기기 전에는 절대 환불하지 마라”가 함께 있는 경우다. 지시를 충실히 따르는 모델일수록 이런 충돌이 성능을 떨어뜨릴 수 있다. |
| **구식 설정**            | 이전 Claude 세대를 위해 작성한 수동 사고 토큰 예산 같은 설정은 최신 모델에서 API 요청 거부를 일으킬 수 있다.                                 |

**어떻게 개선할 수 있을까?**

우리는 이런 안티패턴을 찾아내는 명령어를 claude-api 스킬에 추가했다.

Claude Code에서 다음 명령어로 프롬프트, 스킬, 도구 설명을 점검할 수 있다.

`/claude-api prompt-audit`

이 명령어는 현재 작업 디렉터리 안의 관련 내용을 점검한다. Claude API를 호출하는 애플리케이션 코드뿐 아니라, `CLAUDE.md`나 스킬 같은 Claude Code 자체 설정도 대상이다.

예를 들어 우리는 고객 지원 벤치마크에서 **Opus 4.8에서 Opus 5로 전환하는 상황**을 실험했다.

먼저 문제가 없는 프롬프트를 준비한 뒤, 다음 안티패턴을 하나씩 넣어 총 여섯 개의 기존 방식 프롬프트를 만들었다.

* 더 이상 지원되지 않는 사고 설정
* 서로 모순되는 환불 규칙
* 수동으로 작성하게 한 사고용 작업 메모
* “두 번 검증해라”
* “최대한 철저하게 해라”
* 반드시 따라야 하는 6단계 절차

각 프롬프트를 다음 세 가지 조건에서 실행했다.

1. Opus 4.8에서 실행
2. 프롬프트는 그대로 두고 모델 ID만 Opus 5로 변경
3. 프롬프트마다 `prompt-audit`를 한 번 적용한 뒤 Opus 5에서 실행

Opus 5는 “두 번 검증해라”라는 지시 때문에 환불할 때마다 주문 조회를 중복 수행했다. “최대한 철저하게 해라”라는 지시는 수십 번의 불필요한 지식베이스 검색으로 이어졌다.

`prompt-audit`로 안티패턴을 제거하자, **평균 비용은 14.6% 감소하고 정확도는 5.3% 높아졌다.**

비용이 줄어든 이유는 불필요한 도구 호출과 중복 추론이 사라졌기 때문이다. 정확도가 높아진 데에는 세 가지 이유가 있었다.

* **지원이 종료된 사고 설정을 제거했다.**
  이 설정 때문에 고객 문의를 적절한 경로로 분류하는 API 요청이 모두 거부되고 있었다.

* **모순되는 환불 규칙을 정리했다.**
  기존 규칙에서는 Opus 5가 환불해야 하는 네 건을 처리하지 않고, 고객에게 확인을 요청하며 보류했다.

* **수동 사고 메모와 모델 자체 추론의 충돌을 없앴다.**
  세 건의 문의에서 모델은 사고 과정 안에 도구 호출을 글로 적기만 하고, 실제로는 실행하지 않았다.

**3. 추론 강도: Effort**

[Effort](https://platform.claude.com/docs/en/build-with-claude/effort)는 Claude에게 **“이 작업에 얼마나 많은 노력을 들일지”** 알려주는 설정이다.

낮게 설정하면 대체로 더 빨리 결론에 도달한다. 높게 설정하면 답변 전에 더 오래 생각하고, 검증하고, 대안을 탐색한다.

다만 같은 모델에서도 추론 강도에 따른 비용과 성능의 관계는 작업마다 다르다.

예를 들어 가장 어려운 50개 작업으로 구성된 **FrontierCode Diamond**에서 Claude Fable 5의 결과는 다음과 같았다.

| 추론 강도 |    점수 |  작업당 비용 |
| ----- | ----: | ------: |
| Low   | 11.5% |  5.35달러 |
| Max   | 30.9% | 19.00달러 |

추론 강도를 올리자 점수는 약 **2.7배**, 약 **19%포인트** 높아졌다. 비용은 약 **3.5배**가 됐다.

반면 Claude Fable 5.1을 **Humanity’s Last Exam의 도구 미사용 조건**에서 평가하면, 처음에는 성능이 크게 좋아지지만 마지막 단계에서는 개선 폭이 작아졌다.

* Low: 약 53%, 문항당 약 0.30달러
* Max: 약 61%, 문항당 약 2.23달러

특히 Max 바로 아래 단계에서 Max로 올렸을 때는 **비용이 46% 늘어났지만 점수는 약 0.5%포인트만 상승**했다. 이 차이는 벤치마크를 반복 실행할 때 생기는 변동 범위 안에 있었다. 즉, 측정 가능한 성능 개선 없이 돈을 더 쓰는 셈이다.

추론 강도는 너무 높아도, 너무 낮아도 문제가 된다.

**“높을수록 무조건 좋다”고 생각하는 경우**

높은 추론 강도는 과도한 고민을 유발할 수 있다. 작업에 필요한 수준보다 오래 생각하면서 비용과 지연 시간이 늘어나고, 답변 품질이 오히려 떨어질 수도 있다. 추가로 찾아낼 근거가 남아 있을 때에만 더 많은 숙고가 도움이 된다.

**무조건 낮은 추론 강도를 선택하는 경우**

너무 낮게 설정하면 충분한 근거를 확보하기 전에 멈출 수 있다. 도구를 적게 호출하면서 세 번째 검색 결과까지 확인하지 않고 첫 번째 결과만 보고 답할 수 있다. 어려운 단계에서 충분히 생각하지 않거나, 평소라면 스스로 수행했을 검증을 건너뛰기도 한다.

겉으로는 완성된 답처럼 보여도, 실제로는 일부 정보만으로 만든 답일 수 있다.

**어떻게 조절하면 좋을까?**

**① 더 강한 모델을 낮은 추론 강도로 시험해 보자.**

성능이 더 좋은 모델을 낮은 강도로 쓰는 편이, 성능이 낮은 모델을 높은 강도로 쓰는 것보다 저렴할 수 있다.

예를 들어 **CursorBench 3.2**에서 Claude Fable 5.1의 Low 설정은 Fable 5의 High 설정과 같은 수준의 성능을 내면서, 비용은 약 **3분의 1**이었다.

새 모델이 더 저렴한 이유는 두 가지다.

* 낮은 추론 강도에서 작업당 수행하는 연산과 작업량이 적다.
* 프롬프트 캐시 읽기 가격이 더 저렴하다. Fable 5.1은 100만 토큰당 0.25달러이고, Fable 5는 1.00달러다.

가격 차이를 없애고 Fable 5의 요금을 적용하더라도, Fable 5.1을 Low로 사용하는 비용은 약 **40% 적다.**

**② 작업의 특성을 파악하자.**

여러 추론 강도에서 애플리케이션을 평가하면, 해당 작업에서 비용과 성능이 어떻게 달라지는지 알 수 있다.

평가 점수가 이미 상한에 도달한 상황이 아닌데도 추론 강도를 바꿔 봐야 성능이 거의 같다면, 그 작업의 병목은 추론 연산량이 아닐 가능성이 크다. 이런 경우 강도를 높여도 도움이 되지 않는다.

이런 조정에는 보통 여러 모델과 추론 강도를 조합한 평가가 필요하다. Claude Code에서는 다음 명령어가 이를 탐색해 준다.

`/claude-api hillclimb`

이 명령어는 평가 데이터를 **설정을 개선하는 데 사용할 데이터와 최종 검증용 데이터**로 나눈다. 그런 다음 설정 변경을 제안하고, 개선용 데이터에서 실패한 사례를 읽으며 문제를 수정한다.

여기서 데이터 분할은 프롬프트와 설정을 최적화하고 검증하기 위한 것이다.

**고객 지원 벤치마크에서의 적용 사례**

우리는 기본 추론 강도인 High로 설정한 Opus 4.8에서 출발했다.

먼저 `hillclimb`은 **Opus 5의 Low 설정**을 시험했다. 동시에 `prompt-audit`를 적용해 불필요한 도구 호출 절차, 사고 메모 작성 단계, 모순되는 규칙을 제거했다.

그 결과 개선용 데이터에서 정확도 **98.9%**를 기록하며 Opus 4.8 기준 성능을 넘어섰고, 비용은 **문의 한 건당 2.6센트**로 줄었다.

다음으로 더 저렴한 **Sonnet 5의 Low 설정**을 시험했다. 비용은 건당 **1센트**까지 내려갔지만 정확도도 **88.9%**로 떨어졌다.

Claude는 실패한 문의들을 읽고, 문의 분류 규칙과 환불 한도 참조 지침을 프롬프트에 추가했다. 그러자 비용은 그대로 유지하면서 정확도가 다시 **98.9%**로 올라갔다.

탐색 과정에서 한 번도 사용하지 않은 별도의 문의 14건으로 최종 평가했을 때, 원래 설정의 점수는 **78.6%**, 최종 설정의 점수는 **90.5%**였다. 비용은 원래의 약 **5분의 1**이었다.

**4. 비용 절감 자동화하기**

프롬프트 캐싱, 지시문, 추론 강도는 비용을 줄이는 대표적인 방법이다. [공식 문서](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence#cut-spend-without-losing-quality)에서는 더 다양한 방법을 다룬다.

Claude API를 사용하는 애플리케이션 코드를 종합적으로 점검할 수 있도록, 다음 명령어도 추가했다.

`/claude-api cost-optimize`

이 명령어는 비용이 어디에서 발생하는지 분석하고, 비용 절감 조치를 적용한다. 평가 데이터까지 제공하면 비용을 줄였을 때 성능이 어떻게 달라지는지도 보여준다.

먼저 다음 자료를 이용해 토큰이 어디에 사용되는지 파악한다.

1. **Claude Admin API 키가 있다면:** 조직의 사용량 및 비용 보고서
2. **애플리케이션이 사용량을 기록한다면:** 각 API 응답의 `usage` 객체
3. **둘 다 없다면:** 요청을 구성하는 코드를 읽어 사용량 추정

이후 가능한 비용 절감 방법의 우선순위를 정한다.

* 프롬프트 캐싱 개선
* `prompt-audit`를 포함해 요청마다 전달하는 내용 줄이기
* 출력 길이 제한
* 즉시 응답이 필요하지 않은 작업을 배치 처리하기

평가 데이터를 제공하면, 여기서 더 나아가 추론 강도와 모델 조합별 비용 및 성능도 계산한다.

우리는 Sonnet 5를 기본 모델로 삼아 네 가지 공개 벤치마크에서 이를 실행했다.

**LegalBench: 비용 약 58% 절감**

`cost-optimize`는 여러 작업이 공유하는 프롬프트 앞부분을 캐시하고, 추론 강도를 Low로 설정하며, Batch API로 작업을 처리하도록 제안했다.

사고 토큰은 **102,779개에서 8,284개**로 줄었다. 통과율 변화는 평가의 변동 범위 안에 머물렀고, 비용은 약 **58% 감소**했다.

**tau2-bench retail: 비용 약 73% 절감**

캐시 경계점을 명시적으로 배치해 프롬프트 캐싱을 적용했다. 통과율을 유지하면서 비용을 줄였다. 원문 본문에서는 절감률을 **72%**로 표기한다.

**OfficeQA Pro: 비용 약 52% 절감**

배치 처리와 문서 캐싱을 추가했다. 비용은 **136.20달러에서 64.87달러**로 줄었다.

**SWE-bench Verified: 비용 약 55% 절감**

기본 설정에서 이미 캐싱은 올바르게 작동하고 있었다.

따라서 추론 강도를 Medium으로 낮추고, 에이전트의 출력을 간결한 몇 문장으로 제한해 비용을 줄였다.

작업당 수행 단계 수의 중앙값은 **29단계에서 17단계**로 줄었고, 프롬프트 토큰은 **7,520만 개에서 3,370만 개**로 감소했다.

**5. 시작하는 방법**

목적에 따라 다음 명령어를 사용하면 된다.
